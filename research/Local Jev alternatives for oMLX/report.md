# Run Jeff on MLX, not oMLX, for Jev

There is no local copy of Jev itself: **TypeSafe has not released Jev's weights, architecture or training recipe**. But within two weeks of launch the `POST /v1/systemone` request format became an open protocol. Dozens of open-weight models and servers now accept the same `choice`/`noul`/`score` request and return per-option probabilities and `confidence`. Several of them run natively on Apple Silicon. oMLX is the wrong host for any of them today. **It returns no logprobs on any endpoint**, and the pull request that adds them is still unmerged. So the only Jev stand-in that runs *inside* oMLX, githubnext/localjev, has the model write its probabilities out as JSON, which is slow (0.5–1.2 s p50) and uncalibrated. The bot's workload is smaller than it looks. Its logged states have a median of about 2,700 characters (roughly 1,400 input tokens per call once the questions are added), usually 2–8 options, and never more than 20. That fits comfortably in small decision models. **Try first: firelex/jeff (`Jeff-Qwen3.5-0.8B`, MLX backend) behind its own `/v1/systemone` server.** It is a purpose-built Jev clone with choice, noul and score, up to 254 options, a reported calibration error of 0.021, and 28 ms per decision on an M4 Max. The bot needs only one change: a configurable endpoint. SemIf's MLX backend over Qwen3.5-4B is the fallback with a stronger model. The 109,000 Jev decisions already in `runs/`, each with full probability distributions, are what make any local switch safe: they are a ready-made test set and calibration set.

## The "long state" is only about 1,400 tokens and 17% of wall time

The size of the context decides which models are usable, so the bot's own logs come first. Across 109,039 logged decisions in `runs/*/decisions.jsonl`, the `state` string has a median of 2,674 characters, a 95th percentile of 3,276 and a maximum of 5,029. `n_options` has a median of 2, a p95 of 8 and a maximum of 20. The spend ledger (`runs/budget.json`) shows 62,196 calls for $3.58. At $0.042 per million tokens that is **about 1,370 input tokens per call**, including the option descriptions. Each record stores Jev's full `probabilities` map, its `confidence` and the `noul` danger score, next to the state and the criteria. So the log is already a labeled dataset.

The same records set the latency budget. With keep-alive, hosted Jev's median is **about 101 ms (p90 149 ms)**, and the journal records that "prompt size and option count don't affect latency". A later measurement found that **Jev calls take only 17% of wall time**, and the harness itself takes about 490 ms per decision (`JOURNAL.md`). So a local picker at 100–300 ms would barely change play speed. Money is also not a reason to go local, because Jev costs a few dollars per hundred thousand calls. The real reasons are no network dependency, no early-access waitlist or spend cap, the ability to fine-tune on NetHack, and freedom from a terms of service that reportedly restricted benchmarking at one point ([HN 49812769](https://news.ycombinator.com/item?id=49812769)).

A 1,400-token state rules out some of the fastest clones and keeps others. Laya's default window is 1,024 tokens and Verdict's is 512, so both would truncate the state. Laya's multilingual checkpoint reads up to 8,192 tokens ([laya](https://github.com/NandhaKishorM/laya)), and the Qwen- and Gemma-based clones have windows far larger than the bot needs.

## Jev stayed closed, but /v1/systemone became a commodity

TypeSafe launched Jev on 2026-09-14 as a hosted "System One" model with one endpoint and three typed question kinds. It describes its method only as "a new model architecture, parallel sampler … and training method we call Reinforcement Learning for Calibrated Decisions (RLCD)" ([TypeSafe blog](https://typesafe.ai/blog/introducing-system-one-models-and-jev)). The CEO called the architecture "close to the chest" on HN ([Victor Dibia](https://victordibia.com/explainers/jev/)). The API, however, is fully documented. A request is `model` + `state` + a `questions` map. `choice` returns `choice`, `probabilities` and `confidence`, `noul` returns a 0–1 probability, and all questions are scored in parallel against the same state without seeing each other ([docs.rs typesafe-jev](https://docs.rs/typesafe-jev/latest/typesafe_jev/)). That simplicity produced four groups of clones within days.

**Dedicated open-weight decision models** are the closest thing to a local Jev. **Jeff** (firelex/jeff) fine-tunes Qwen3.5-0.8B/2B and Gemma 4 E2B for zero-shot choice/noul/score. It reports 79.1% (0.8B) and 82.0% (2B) on five benchmarks against Jev's published 83.0%, and **28 ms per decision on an M4 Max with `JEFF_BACKEND=mlx`** ([GitHub](https://github.com/firelex/jeff)). v1.1 (released 2026-09-29) raised the maximum number of options from 26 to 254 with a trained 255-way readout head and fitted temperature ([release](https://github.com/firelex/jeff/releases/tag/v1.1)). The model card reports calibration error 0.021, and the weights are Apache-2.0 ([HF](https://huggingface.co/mstrasser/Jeff-Qwen3.5-0.8B)). **Kev** (jaredpalmer/kev) ships Qwen-based 0.8B–27B checkpoints, each with a fitted temperature, and a `/v1/systemone` server that the TypeSafe SDK talks to unchanged. On new-source accuracy Kev-4B scores 0.817 against Jev's 0.857, but on an Apple M5 it takes **721 ms for five questions (136 ms with the text cached)** ([GitHub](https://github.com/jaredpalmer/kev)). **Laya**, a 421M/322M ModernBERT encoder, is by far the fastest on a Mac: 7–13 ms P50 through laya-mlx and about 5 ms through Core ML on an M3 Max ([laya-mlx](https://github.com/mizorewww/laya-mlx), [laya-coreml](https://github.com/mizorewww/laya-coreml)). It collapses on large label sets, though: 0.425 vs Jev's 0.870 on the 77-intent Banking77 ([laya-ai.com](https://laya-ai.com/jev-alternatives)). HN users report that the gap to Jev "widened" on harder queries ([HN 49848269](https://news.ycombinator.com/item?id=49848269)). Von (395M ModernBERT, MPS), Decider, Tev1, JevK5 and NanoJev fill out this group ([von](https://github.com/wfzyx/von), [Decider](https://github.com/Mapika/decider), [Tev1](https://github.com/togethercomputer/tev1), [NanoJev](https://github.com/TianyuCodings/NanoJev)).

**Readout servers** turn any open LLM into a Jev endpoint by reading the logits of the declared options at one position instead of generating text. **SemIf** (formerly OpenJev) has a **native MLX backend**. Its shared-state mode prefills the state once and branches across all the questions, and it added per-workload temperature calibration on 2026-09-22. On an RTX 3090 it answered 21 binary criteria in 1.02 s, against 5.33 s for generated JSON ([GitHub](https://github.com/TheoLeeCJ/SemIf-OpenJev)). daseinlabs/open-jev defaults to MLX on Apple Silicon at about 90 ms per request with Gemma 3 4B ([GitHub](https://github.com/daseinlabs/open-jev)). razorback16/openjev serves DiffusionGemma 26B-A4B through MLX and also accepts the `jev-latest` alias ([GitHub](https://github.com/razorback16/openjev)). khimaros/verdict, llamacpp-jev and the `jevper` library do the same over llama.cpp or any OpenAI-compatible logprob source ([verdict](https://github.com/khimaros/verdict), [jevper](https://pypi.org/project/jevper/)). The core trick fits in "Jev in 25 Lines of Python" ([HN](https://news.ycombinator.com/item?id=49812769)).

**Runtimes** package these models. Ollaya ("Ollama for decision models") serves `/v1/systemone` on `localhost:11435`, and the TypeSafe SDK works unchanged. **On Macs, though, only laya and nli use the GPU. The rest run on CPU** ([ollaya.dev](https://ollaya.dev/), [Glonce](https://glonce.com/ollaya-runs-typesafe-jev-decision-models-locally-ollama/)). **Prompted JSON stand-ins** are the last group, and the only one that runs on oMLX, as the next section explains.

| Candidate | Mac backend | Context vs. bot's ~1.4k tokens | Probabilities | Reported Mac latency |
|---|---|---|---|---|
| Jeff-Qwen3.5-0.8B / 2B | MLX | Fits | Trained readout head + fitted temperature | 28 / 60 ms, short prompt (M4 Max) |
| SemIf + Qwen3.5-4B | MLX, MPS, llama.cpp | Fits | Logit readout, optional calibration | None published |
| Kev-4B | MLX | Fits | Readout + fitted temperature | 721 ms for 5 questions, 136 ms cached (M5) |
| Laya multilingual (laya-mlx) | MLX / Core ML | Fits (8,192) | RLCD-style trained | 7–13 ms, short prompt (M3 Max) |
| daseinlabs/open-jev (Gemma 3 4B) | MLX | Fits | Option scoring | ~90 ms |
| LocalJev over oMLX | oMLX | Fits | Self-reported JSON | 0.52–1.21 s p50 (M5 Max) |

Every latency figure here comes from each project's own author, measured on short inputs. No independent benchmark compares them under one protocol, and several repos passed thousands of stars in days, which awesome-jev warns about ([awesome-jev](https://github.com/yibie/awesome-jev)).

## oMLX can pick an option but cannot say how sure it is

The locally installed oMLX is 0.5.7. Upstream stable is v0.6.4, and v0.7.0rc1 came out on 2026-09-24 ([releases](https://github.com/jundot/omlx/releases)). **No version returns logprobs.** The request models have no `logprobs`, `top_logprobs` or `logit_bias` fields, and the scheduler throws away mlx-lm's per-token logprobs. Issue #1549 documents that `/v1/chat/completions` accepts `logprobs: true` but returns empty content ([#1549](https://github.com/jundot/omlx/issues/1549)). PR #1591, open since 2026-06-02, adds OpenAI-style logprobs to chat only. By design it **omits them when `response_format` is set or a tool or reasoning parser is active**. A live test on 2026-09-29 found that logprobs were still missing for a Gemma 4 model even without a JSON schema ([PR #1591](https://github.com/jundot/omlx/pull/1591)). The v0.7.0rc1 notes do not mention it. So "constrain the output to the options, then read the option distribution" cannot be done in oMLX, and the Qwen3.x models the bot would use go through exactly the parser path that the PR suppresses.

oMLX does have good structured output. On `/v1/chat/completions` it accepts `response_format` JSON schemas and a vLLM-style `structured_outputs` object with `choice`, `regex` and EBNF `grammar`, enforced by xgrammar token masking ([README](https://github.com/jundot/omlx)). A `choice` list with `temperature: 0` (the local default is 1.0) and thinking disabled returns exactly one valid option id in a few decode steps. That is the argmax **without a distribution, a confidence or a calibrated noul**. The bot's safety rubric needs those, because it overrides the pick when danger is 0.6 or higher. oMLX's `/v1/rerank` can serve Qwen3-Reranker, whose score is literally P(yes) over {yes, no}, so it maps onto `noul`. But the prompt is hard-coded to a "web search" instruction, and each document is a separate forward pass that re-encodes the shared query. One measurement put this at about 24 ms per document plus 0.38 ms per query token on Qwen3-Reranker-4B ([#3913](https://github.com/jundot/omlx/issues/3913)). For a 1,400-token state and 8 options, that works out to roughly 4.5 s.

oMLX's real strength is its prefix cache: 256-token paged blocks in RAM with SSD overflow. v0.7.0rc1 adds partial-block reuse, which cut next-turn TTFT from 0.83 s to 0.42 s on a 13.4K-token prompt ([v0.7.0rc1](https://github.com/jundot/omlx/releases/tag/v0.7.0rc1)). That matters less here than it seems. The bot's state begins with a stable preamble (role, standing order, strategy notes), but most of its ~1,400 tokens change every turn, and 1,400 tokens is short enough that prefill is not the bottleneck on a small model.

The in-oMLX option that actually exists is **githubnext/localjev**. It is a Bun server with a `/v1/systemone` front end that prompts an oMLX model to write a JSON probability vector, retries malformed output and normalizes the result. Its README says plainly that these are self-reported probabilities, not logit reads, and that "the normal oMLX API does not expose" the primitives a real readout needs ([GitHub](https://github.com/githubnext/localjev)). On an M5 Max its best models reached 74–77% macro accuracy at 0.52–1.21 s p50 ([jevainews](https://jevainews.com/news/github-next-localjev/)). That is 5–12× slower than hosted Jev, and the confidence values carry no calibration guarantee. If the bot must keep oMLX as its only runtime, the practical escape is the `mlx_lm.server` bundled inside oMLX.app (mlx-lm 0.31.3). Its completions endpoint returns `top_logprobs` and accepts `logit_bias` ([SERVER.md](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/SERVER.md)), so a thin shim can do first-token option-letter readout on the same model files. vllm-mlx silently drops logprobs ([#786](https://github.com/waybarrios/vllm-mlx/issues/786)), and Ollama's logprobs change greedy outputs and ignore temperature ([#18163](https://github.com/ollama/ollama/issues/18163), [#16196](https://github.com/ollama/ollama/issues/16196)), so neither is a better host.

## Try Jeff-0.8B first, SemIf-4B second, and score both against logged Jev

**Jeff is the right first experiment** because it matches the bot on every axis that matters. It is wire-compatible, so the three per-turn questions (action choice, danger noul, safest choice) go through unchanged. It returns a per-option probability map and confidence, so the danger-override rubric keeps working. v1.1's 254-option limit leaves plenty of room above the bot's maximum of 20. It runs on MLX. Its authors also show the approach can be fine-tuned for one game: they ship Jeff-Qwen3.5-0.8B-Chess, and the SFT took about two hours on one GPU ([firelex/jeff](https://github.com/firelex/jeff), [HF](https://huggingface.co/mstrasser/Jeff-Qwen3.5-0.8B)). Two things are still unknown. First, the 28 ms figure was measured on short prompts, and Jeff's latency on a 1,400-token state is unmeasured. Second, no mlx-community quantization exists, and its custom readout head needs Jeff's own loader. So run Jeff's server rather than trying to load it into oMLX. The model card also warns that it "won't match" frontier models on multi-step reasoning. NetHack tactics are exactly that kind of task, so measured agreement with Jev, not the benchmark tables, should decide.

The bot needs only one change. `jev/jevapi.py` hard-codes `ENDPOINT = 'https://api.typesafe.ai/v1/systemone'` and always opens an `HTTPSConnection` with a TLS context. Reading the endpoint from an environment variable, and using plain `http.client.HTTPConnection` when the scheme is `http`, lets the same client talk to Jeff, SemIf, Kev or Ollaya on localhost. The client's check that `choice` is one of the `criteria` keys already guards against a local server returning a malformed answer.

If Jeff-0.8B disagrees with Jev too often on hard tactical states, the next step is **SemIf with `--backend mlx` over Qwen3.5-4B**. It uses a larger, unmodified model, and its shared-state mode matches the bot's pattern of one state with three questions ([SemIf](https://github.com/TheoLeeCJ/SemIf-OpenJev)). Raw readout from instruct models is overconfident. In Victor Dibia's tests, instruct models had ECE 0.10–0.18 against 0.02–0.05 for base models, and temperature scaling on 600 labels brought a 7B instruct model from 0.10 down to 0.03 ([victordibia.com](https://victordibia.com/explainers/jev/)). So run SemIf's calibration step before trusting its danger scores. Kev-4B is a comparable alternative with a fitted temperature included, but its 136–721 ms on an M5 is at the slow edge of the budget ([Kev](https://github.com/jaredpalmer/kev)). Laya on laya-mlx is worth one run as a speed baseline with the multilingual 8K checkpoint. Its weakness on large label sets and on harder reasoning makes it an unlikely winner, though the bot's median of two options does soften that weakness.

The evaluation is cheap, because the data already exists. Replay a few thousand logged `decisions.jsonl` records through each local server. Measure top-1 agreement with Jev's `choice`, the KL divergence or Brier score against Jev's full `probabilities`, and the error on `danger` around the 0.6 threshold. Report the danger error separately, because the safety override depends on it more than on overall accuracy. This is the "prototype on Jev, collect labels, fine-tune a small open model" workflow the community settled on. One report puts Kev-4B's gain on one workload at 67.7% to 73.6% for about $1 of H100 time ([stackness](https://stackness.dev/blog/how-do-you-run-system-one-decision-models-locally-ollaya-laya-mlx-and-the-runtime-slot)). Tools such as stuntd and Jevstiller automate the same distillation loop ([stuntd](https://bittide.aicompass.dev/article/012b16f3-88e1-482f-a40d-2c51ffbd0ad8), [HN](https://news.ycombinator.com/item?id=49891769)).

## Conclusion

The question "is there a local Jev for oMLX" has a split answer. There are plenty of local Jevs, but oMLX is not where they run. Until PR #1591 merges *and* works alongside constrained decoding and reasoning parsers, oMLX can only choose an option, not score it, and the bot's safety logic depends on scores. The sensible design keeps oMLX for what it does well, such as long-context generation with the installed 27B model, and puts a dedicated MLX decision server next to it on another port, speaking the protocol the bot already uses.

The bigger opportunity is less obvious. With 109,000 full Jev probability distributions over real NetHack states, the bot already holds the dataset that the community calls the real advantage behind Jev ([HN 49848269](https://news.ycombinator.com/item?id=49848269)). A Jeff-0.8B fine-tuned on those logs, with a temperature fitted to the danger scores, is a realistic path to a local picker that matches Jev on *this* game, including its narrow distribution of 2–8 options per turn, even though no general-purpose open model yet matches Jev across all tasks.
